# Software, design and industrial engineering review

Independent assessment prepared before the other panels' arguments were shared. The review uses the pre-council checkout `e90cca2`, the two stable release commits and primary sources consulted on 24 November 2026. The three disciplinary perspectives share one reviewer. The two host traces and source evidence below can support or overturn its conclusions.

## Software engineering

The emitted loading sequence assumes a control the powered chip host cannot operate as specified. The exact Tiny Tapeout IHP template locked by this project describes user-module `ena` as high when the design has power. The organizer lists 8 inputs, 8 outputs, 8 bidirectional pins, clock and reset, and says deselection loses state. The G3 assembler uses low enable for reset/identification, every byte and register read and two clocks after leaving loader mode. The final two clocks let the input registers capture idle while the ready engine stays at PC zero. Connecting `ena` to the project-select control cannot realize those clocks on the active project. This affects the handoff to the intended host and the post-fabrication reprogramming claim. The macro's GDS, readback and historical pin-level results retain their tested meaning. [Pinned IHP template, user module port declaration](https://github.com/TinyTapeout/ttihp-verilog-template/blob/4b1204ab387b5ab94db1d57067051d8d89a2f83c/src/project.v#L13) · [Organizer FAQ, pins, loading and reset](https://blog.janestreet.com/protocol-emulator-asic-competition/#faq) · [Frozen G4 loader](https://github.com/KG-khangelani/protocol-emulator-asic/blob/5bdc0e6b6449a829a5da1f8f9a8060257e974843/tools/assembler.py#L344)

The unmodified release assembler rebuilt all thirteen G4 images to the independent word catalog and both G5 images to the eight published per-program files. For a program of W words, the released plan requires `8W + 2 ceil(W/8) + 10` pre-execution rising edges. Its `4W + 7` low-enable requests include the four bytes read per word. The 96-word combined I2C example takes 802 steps with 391 low-enable requests. Its 384-byte binary generates a 170,919-byte pretty-printed plan. The plan is convenient host-side audit material. An embedded interpreter can stream the byte image and regenerate this regular access pattern if audited against every plan step. These counts measure logical transactions and file size. Host polling/transport timing requires a separate measurement.

**Fresh digital screen.** Two paths left all released program bytes intact. Tying enable high without adjusting the released plan advanced PC by one on the first flush for every example. A new host sequence kept enable high throughout, selected `0xE7` for both flush edges, released host UIO and applied the declared idle. The existing selector ignores writes to register 7, releases the chip's bidirectional outputs in write mode, retains program/data and holds the engine in reset. The independent input synchronizer clocks normally. With `ui=0` on the following rising edge, all checks agreed. [ISA register table](https://github.com/KG-khangelani/protocol-emulator-asic/blob/5bdc0e6b6449a829a5da1f8f9a8060257e974843/docs/isa.md#L132) · [Top-level decode and engine reset](https://github.com/KG-khangelani/protocol-emulator-asic/blob/5bdc0e6b6449a829a5da1f8f9a8060257e974843/src/project.v#L57) · [Writable payload registers](https://github.com/KG-khangelani/protocol-emulator-asic/blob/5bdc0e6b6449a829a5da1f8f9a8060257e974843/src/m1_data_store.v#L23)

| Observation | Reference macro plan | Simply hold enable high | Powered `0xE7` flush |
|---|---:|---:|---:|
| First-flush dedicated status, all 15 programs | 0x20 | 0x21 | 0x20 |
| Programs matching all sampled reference runtime pad levels and dedicated status | 15 | 0 | 15 |
| Positive-path loader steps across 15 programs | 2,890 | All 15 plans failed at flush | 2,890 |

Each positive path exercised 9,811 runtime edges, 8,691 of them on full two-frame UART TX. Both G5 traces matched the separate frozen event tables including the selected two-clock edge change, HALT and post-HALT hold. The remaining examples used 80 edges of idle-environment stimulus each. Their protocol exchanges, aborts and arbitrary input phases still need wider coverage on this host path. Changing the first combined-I2C program write from 0 to 1 failed the very first byte readback at zero-based loader step 399. Its first 80 runtime pad/status/enable observations happened to agree with the good image, illustrating why a short run cannot replace readback. An independent projection using only sensed pads and the dedicated output reproduced the 15/15 distinction. The first harness stopped on an unknown first edge from a time-zero initialization issue. Its subsequent run explicitly drove the same reset vector before the first rising edge. Counts, controls and budgets stayed fixed. The passing run used a cached local Icarus 14 development build and two hash-checked vendor models. Program bytes, runtime observations and gates are reproducible with the scripts alongside this review. [Screen contract](contract.md) · [Prospective harness correction](reset-amendment.md)

**Weakness in the proposed repair.** The runner changes logical inputs simultaneously, models weak static bias, observes ideal settled levels and can instrument chip output enables. An operator can sense a resolved pin. The demo board provides no dedicated readout of the internal `uio_oe` bus, and matching a driven value cannot prove that a pin has released. Test an actual break-before-make transition with the host's external drivers off while the chip changes from read to write. Establish project clock control, peer isolation and settling explicitly. On exiting `E7`, one candidate guard is to deassert only `ui[7]` to reach `67` with the clock parked low, then set `00` before the first run edge. This intermediate selector avoids an unintended loader-read decode from skew on `ui[7:6]`. That sub-edge sequence remains a proposal.

## Design and owner use

The source-to-word-to-cycle path is inspectable. The versioned assembler emits a listing with edge numbers for fixed computation and explicitly stops timing expansion at an external choice. The catalog holds independently encoded words and prevents an edited source from silently becoming its own answer. The 96-word combined I2C example leaves 32 usable words, and the G5 example uses 20. These references support a teaching exercise in which a reader predicts a transition, changes two waits, rebuilds the image and locates the consequences in a trace. The G5 retained first attempt rejected `#` comments, a concrete example of the difference between machine reproducibility and first-use ergonomics. The guide already documents the language and the released evidence already runs outside the source tree. [Programming guide](https://github.com/KG-khangelani/protocol-emulator-asic/blob/5bdc0e6b6449a829a5da1f8f9a8060257e974843/docs/programming.md) · [G5 qualification and first rejection](https://github.com/KG-khangelani/protocol-emulator-asic/tree/e90cca228490423a7fe7c4ae40f7e669200b4d0e/evidence/E0048-waveform-replay)

The project declares owner learning equal to engineering. Its active M0 teach-back asks the owner to predict a waveform row and distinguish generic synthesis from the evidence in E0010. A council, an agent's run or a questionnaire with model-supplied answers cannot fulfill that requirement. A separate first-time-reader test can assess the technical write-up and ease of modifying a program. Freeze the reader, machine, task, success criteria and allowed help. Measure correct completion, time, hints, errors and one short account of confusion. These measure the performance of the readers sampled. [Project learning goal](https://github.com/KG-khangelani/protocol-emulator-asic/blob/e90cca228490423a7fe7c4ae40f7e669200b4d0e/docs/goal.md) · [Existing checkpoints](https://github.com/KG-khangelani/protocol-emulator-asic/blob/e90cca228490423a7fe7c4ae40f7e669200b4d0e/docs/learning/checkpoints.md) · [NISTIR 7432, context, criteria and test method](https://www.nist.gov/publications/common-industry-specification-usability-requirements)

**Weakness in this proposal.** Two convenient readers supply evidence of observed friction with little statistical power. Timing the owner while they learn may reward rushing. Keep that owner's supported teaching and transfer to a second problem separate from a cold reviewer task. Direct maintainer assistance changes the usability result and should be recorded. Prefer modifying a reproducibly confusing passage over adding an abstraction layer on speculation. A narrow source macro for the repeated I2C clock-stretch block is plausible if a reader repeatedly edits the wrong wait. Expanding such a macro preserves executable word count, runtime and SRAM area.

## Industrial engineering

Two retained physical jobs give an order-of-magnitude cost for a future qualification. The first and second G4 workflows took 5,899 s and 5,679 s from first job start to last completion. Their job time totals were 6,174 s and 6,030 s with precheck and netlist testing partly parallel. GDS accounted for 3,902 s and 3,332 s. Those times exclude design, debugging, queueing before the first job, publication, and gate rework after a failure. D46 changed two specific Magic rule files against pinned evidence. D47 adjusted the ports exported from existing supply conductors after a 148-error LEF failure. Any future PDK/flow promotion needs explicit review of those assumptions and the full checker. E0047 supplies two reproducible runs under one physical configuration. Foundry manufacturing yield, board interoperability and acceptance of a future process remain open. [G4 original physical runs](https://github.com/KG-khangelani/protocol-emulator-asic/tree/e90cca228490423a7fe7c4ae40f7e669200b4d0e/evidence/E0047-g4-submission-candidate) · [D46 rule provenance](https://github.com/KG-khangelani/protocol-emulator-asic/blob/e90cca228490423a7fe7c4ae40f7e669200b4d0e/docs/decisions/0046-align-magic-contact-rules-with-pinned-references.md) · [D47 power ports](https://github.com/KG-khangelani/protocol-emulator-asic/blob/e90cca228490423a7fe7c4ae40f7e669200b4d0e/docs/decisions/0047-export-existing-full-height-supply-ports.md)

At G4 release source, 4,080 Git blob paths contain 911,202,781 logical file bytes. Evidence accounts for 908,791,000 across 3,643 paths, about 99.74%. These are file bytes before deduplication or transfer compression. The retained release metadata sizes the G4 submission bundle at 14,869,969 bytes and the G5 standalone program bundle at 244,576 bytes. Give a reviewer the small software path first, then a citation path into the retained physical runs when they examine a physical claim. No evidence deletion or repackaging is needed. G4's 35 release assets record physical/submission materials and G5's 22 assets record the software extension. The organizer gives considerable weight to clear writing and reprogramming, gives no fixed weighting and still shows the final form as forthcoming. No default assumption about a winner, manufactured chip or actual entry follows. [G4 release](https://github.com/KG-khangelani/protocol-emulator-asic/releases/tag/v0.1.0) · [G5 release](https://github.com/KG-khangelani/protocol-emulator-asic/releases/tag/v0.1.1) · [Organizer, submission and judging](https://blog.janestreet.com/protocol-emulator-asic-competition/#faq)

**Weakness in the industrial recommendation.** Holding the current hardware gives up potential architecture advances and leaves electrical behavior unmeasured. The two job histories share tools and input sources. They supply two observed costs and results, with limited predictive power for a new candidate. Maintain a separate matched, capped architecture lane only when a new workload or failure identifies a falsifiable reason to reopen an input.

|---|---|---|
| First, qualify a distinct board-host plan for the existing release | Freeze `ena=1`, host break-before-make timing, readback from physical-pad equivalents, peer isolation and reset behavior. Rebuild unchanged binaries. Exercise two simulators and the existing G4 netlist on the applicable protocol and adverse-input cases. | In parallel, run the existing owner M0 exercise and a cold reviewer task | Owner runs the existing walkthrough, predicts a row, explains the E0010 boundary and responds to a follow-up. | Then test a real host's service and electrical assumptions if suitable hardware is available | For UART, bound interrupt/poll/selector/data settling to cache a tentative first byte before overwrite. A two-stage host can park on `63`, read `62` after detection and monitor ordinary terminal status, with final valid/byte checks. It needs a new watchdog, interruption and timing proof. | Estimate 1 day of host development, one MCU/FPGA and analyzer if already available. The hardware panel should challenge whether the read-only parking selector stays harmless throughout physical switching and whether holding an external partner idle while clocks are parked is achievable. The architecture panel should state which externally specified service task would justify spending the current 32-word program headroom or adding a queue. Either argument could change the ranking. A physical test with the existing FPGA breakout would check host transport and real external loading levels, subject to demonstrating the FPGA store's synchronous read and byte-mask behavior. It would still leave CMOS5L pad and SRAM silicon properties open. [Official FPGA breakout](https://www.tinytapeout.com/guides/fpga-breakout/)
