# From a published asset to a useful program

**What an owner can already start.** On 24 November 2026 the documented commands in the 244,576-byte public v0.1.1 starter built both 20-word examples in a fresh native Windows 11 directory and reproduced all eight packaged artifacts byte for byte. The included waveform-oracle suite passed 12 tests. A deliberate unsupported first line failed with exit 2 and created no output directory. The two assembler subprocesses took 0.130 and 0.135 seconds of wall time on this machine, including interpreter startup. This is evidence about a prepared machine executing two README commands. No participant read the page, interpreted a word, predicted a trace, selected a source archive or diagnosed the error. The package expressly directs users to the checkout and workbench for waveform simulation. Its compact size helps distribution while the full logical checkout is much larger. The small ZIP and the GitHub-generated source tarball serve different starting tasks. **Comparison at equal work.** Neither DS18B20 power-query program was part of the immutable G4 or G5 release. The council supplied the 85-word temporal program and the 32-word PIO program as research materials. Raspberry Pi's published PIO assembler emits the second program. Its measured operation then uses a separate simulator and host fixture. Raspberry Pi's actual SDK example also includes generated PIO headers, PIO/SM allocation, GPIO selection, program initialization, host input to the FIFO and a board-specific executable. For hardware the operator must configure/build or obtain that board firmware, flash it and connect a real target. The ASIC route requires the qualified image, a loader that can actually control the available external signals, pin assignment, a verified target isolation mechanism, settling and a means to read the terminal result. The released macro loader still requests `ena=0`; the staged powered profile has only digital evidence. Neither simulated oracle run replaces these host and commissioning steps. Measure cold acquisition/installation and code-to-working-result separately. The DS18B20 digital comparison used full code readback in both fixtures, separate launch, zero host service between launch and terminal and excluded post-terminal outcome acquisition. One cold ASIC run consumed 712 public clocked setup steps for 85 × 32 bits. Fully verified PIO startup used 115 32-bit MMIO operations and one subsequent enable. The 115 consisted of 32 instruction writes, 32 forced jumps, 32 instruction reads, one PC restore, one FIFO preload, one forced PULL and 16 more configuration operations. Both paths require observing the exposed result. An 8-bit control vector held across a clock, a 32-bit memory-mapped transfer, CPU instructions, a USB transfer and a human operation have different execution times. The fixed controller in the architecture comparison can only implement its compiled task. Cold setup counts or code words alone cannot rank authoring time, power, physical minimality or real elapsed service. A's proposed 6+1 PIO warm operations and C's measured eight-clock warm **I2C** setup have different programs, scopes and evidence. Consecutive rearm for the same power query on both is its own needed test.

**One human task now has verified scope.** Starting with an actual operation, lengthen the reset-low interval from 500 to 516 µs while preserving recovery, the two LSB-first wire commands, slots, terminal marker and absence behavior. In a preregistered software fixture preflight at 15:26 UTC, both programs retained their original image sizes. In all eight target corners and the absent/stuck-low runs on each, the first falling edge stayed fixed, every following DQ edge and the terminal event shifted by exactly 16 µs, and command/terminal results equaled baseline. The original 500 µs scorer rejected each changed trace at reset duration. This demonstrates a common edit with an independent observable outcome. The preflight used Icarus with the VM and the same externally inspected pulses in rp2040js with PIO. Findings apply to the two modeled machines and chosen target. **Human trial, proposed.** Freeze cleaned checkpoints, tool availability, known hardware, run materials, allowed help and two counterbalanced tasks before recruiting. Use the existing G6 owner teach-back as its own rubric. With the owner's consent and one or more independent readers, counterbalance ASIC/PIO order and record their prior language/board exposure. Do a first phase with each ecosystem's normal published entry, recording time to locate the correct physical or tool release, find a known-good program and identify what is still needed for hardware. If an artifact has no equivalent DS18B20 program, record that omission and the time until recognized. In a second phase provide equivalent, pinned comparator packages and an identically prepared environment; make the exact expected edit/time concealed from the participant until the trial. Pre-test a second equivalent timing perturbation if crossover learning would expose the first answer. Require a written prediction, participant-authored source change, an observed legal transaction and the negative control; direct human wall time, hints, restarts and time blocked on download/compilation are different measures. A practical formative cap is 30 minutes per edit, with 1–2 staff-hours per participant for the two phases and debrief. A missed exit criterion identifies a documentation or tool fix. With two readers the outcomes describe those attempts and can expose a recurring problem; they do not estimate population usability. [NISTIR 7432, usability requirements and test method](https://www.nist.gov/publications/common-industry-specification-usability-requirements)

**Priority after debate.** First keep the January submission and owner/reader path visible, publish one clear pointer to G4 physical, G5 software, council prototypes and the exact remaining handoff once the applicable digital/board work passes. The short cold selected-host interlock qualification is an engineering prerequisite to a public board recipe. A single operator must be able to identify peer ownership and clock control; hardware marks require observed physical isolation, timing and repeatable startup. The matched PIO result already removes the argument that expressing only this one new operation demonstrates an unusually small or uniquely usable temporal substrate. Prefer a small matched second workload and a real operator trial before an extensive new layout or protocol expansion. Schedule a physical board/UART campaign earlier when a compatible fixture exists, an external peer is named and its start/service deadline matters. A missed calibrated cold turnaround would promote transport work; repeated human timing/model mistakes would promote diagnostics or examples; a matched second workload retaining a substantial code or service advantage would promote the architecture comparator. A changed organizer form/technology or an actual filing deadline would immediately promote the submission-owner review. The two-run physical receipts, software bundles and cached tools remain valuable through each decision.
