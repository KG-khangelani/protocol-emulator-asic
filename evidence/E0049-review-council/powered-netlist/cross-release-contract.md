# Can a powered host run the published software on the frozen hardware?

The first G3 gate-netlist run used Icarus. Panel C also exercised both G5 images, but that screen did not replay every accepted and rejected waveform case. Before making the board qualification recommendation, compare a second simulation engine and bridge the stable software and hardware milestones.

Use the five unmodified D48 RTL files in Verilator with checked SRAM models. Run every G3 case and the G5 cases compatible with a permanently high project enable. Also run the G5 selection in Icarus on the actual submitted G4 functional netlist with its original hashed PDK/SRAM models. Use the already registered `E7 → 67 → 00` launch and the original images, held stimuli, timing, corrupt-byte control and protocol oracles. The clock monitor must reject any requested low-enable edge.

G5 has one test that deliberately takes two low-enable rising edges to violate a wall-clock contract. A selected project's physical interface cannot issue that operation. Name that case in the output, retain its original release evidence and compare the other twenty individually. Compare their **complete** runtime rows with the original digital archive. In the loader records replace only the intended selector and enable fields of the reference, then require every other field, observed byte, image identity and case disposition to agree. G3 must match all 55 released records, including 15 expected rejections.

The two stages have different evidence levels. Verilator gives an additional RTL execution. The gate-netlist stage is zero-delay Icarus and exercises the exact G4 logic. Neither stage models peer contention, analog loading or wall-clock MCU throughput. The former full digital I²C matrix and selector-contention runs have separate controls. Budget one compile per representation, reuse previously verified inputs, at most 24 MiB working H: space for a stage, and a 16:35 UTC cutoff. Preserve a failed stage or a materialized partial result.
